# Elsewhere v0.2 test plan

## Customer promise under test

Once a remote job is accepted, another Elsewhere process must be able to identify
that exact provider job, report a truthful state, retrieve only its logs, and remove
its temporary resources without claiming success prematurely.

## Automated gates

| Behavior | Proof |
|---|---|
| Existing local leases, routing, trust, source exclusions, and dry plans remain intact | `python3 tests/test_cli.py` |
| Fly and Azure implement the common lifecycle contract | `tests/test_providers.py` contract test |
| Fly retains completed compute for inspection | Plan contains no `--rm` and requires explicit cleanup |
| Fly status and logs select one Machine | Multi-machine response fixture and Machine-ID log assertion |
| Azure uses exit code for success or failure | Terminated response fixtures with exit codes 0 and 17 |
| Missing compute is explicit and never false success | Fly empty-list and Azure not-found fixtures |
| Refresh survives the original process | A new lifecycle call persists identity and normalized state to the jobs file |
| Cleanup is safe to repeat | Two cleanup calls end in `cleaned` |
| Cleanup does not finish before provider absence | Destroy response followed by explicit missing-resource verification |
| Version labels do not disagree | Package, `VERSION`, project metadata, plugin, and MCP source are checked together |
| Supported source and tests compile | `python3 -m compileall -q src tests` |
| Result bundles reject unsafe paths and checksum mismatches | `tests/test_results.py` |
| MCP rejects malformed, uninitialized, missing, extra, and out-of-range input | `tests/test_mcp.py` |
| Concurrent job writers preserve valid state | `tests/test_state.py` |
| Provider output shown during status and cleanup omits account and command internals | public job/provider projections and lifecycle tests |

CI runs the integration test and provider suite on Python 3.11, 3.12, and 3.13.

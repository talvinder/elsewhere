# Design: Elsewhere v0.2 — Dependable remote execution

Generated on 2026-07-17
Branch: main
Repo: talvinder/elsewhere
Status: COMPLETED in v0.2.0a1; see [acceptance evidence](V0.2_ACCEPTANCE.md)
Mode: Builder

## Problem statement

Elsewhere can plan and submit local or remote work, but an accepted remote job does
not yet have a dependable end-to-end lifecycle. Provider status is not normalized
into durable Elsewhere state, short-lived Fly jobs can disappear before their output
is retained, and cleanup does not consistently prove that both compute and source
artifacts are gone.

The v0.2 promise is narrower than the platform vision:

> Once Elsewhere accepts remote work, the user can leave the originating machine,
> later retrieve the exact outcome, and see proof that temporary compute and source
> artifacts were cleaned up.

## What makes this worth building

The useful object is not another cloud wrapper. It is one trustworthy handoff from
an agent or laptop to approved compute. A user should not need to understand a
provider's machine states, log retention, deletion semantics, or regional failure
messages to know whether their work finished safely.

## Constraints

- Preserve provider neutrality.
- Keep all cloud execution behind explicit `--execute` and the active trust receipt.
- Never persist credentials or signed source URLs.
- Reuse Fly, Azure Blob, local leases, trust evaluation, job storage, and MCP tools.
- Keep Python for v0.2; correctness is the constraint, not runtime performance.
- Do not build a new isolation runtime. OpenSandbox and OpenShell remain execution
  options behind the Elsewhere provider/runtime boundary.
- Do not add Vultr until the provider contract and conformance suite exist.
- Preserve the existing `elsewhere` and `agent-capacity` commands during migration.

## Premises

1. The next release should earn trust in one remote job before adding more providers.
2. The provider contract, not the current implementation language, is the durable
   asset.
3. Public issues improve trust and contribution opportunities; only actionable
   security disclosures, credentials, account identifiers, and signed URLs stay
   private.
4. A rewrite before lifecycle semantics stabilize would move defects rather than
   remove them.
5. GitHub remains the open-source distribution channel for v0.2, with a tagged alpha
   release only after fresh-install and live lifecycle proof.

## Approaches considered

### Approach A: Patch the current CLI

Add state refresh, results, and cleanup directly to `cli.py`.

- Effort: small
- Risk: medium
- Advantage: smallest immediate diff
- Cost: preserves provider conditionals throughout a 2,500-line module and makes the
  third adapter more error-prone

### Approach B: Modular Python v0.2

Extract an explicit provider contract and lifecycle state model, migrate Fly and
Azure behind it, add shared conformance tests, then implement result retention and
verified cleanup.

- Effort: medium
- Risk: low to medium
- Advantage: fixes today's failures while making a third provider additive
- Cost: requires a controlled structural change before new behavior lands

### Approach C: Rewrite in Go

Reimplement the CLI, local coordination, trust contract, MCP server, providers, and
tests as a single Go binary.

- Effort: large
- Risk: high
- Advantage: strong cross-platform packaging and a good future daemon runtime
- Cost: discards working behavior, delays user proof, and forces language decisions
  before the workload and provider contracts are stable

## Recommended approach

Choose Approach B. Make the change easy, then make the easy change:

1. Define the state machine and provider contract without changing visible behavior.
2. Put Fly and Azure behind the contract and make both pass the same tests.
3. Persist normalized remote state and provider job identity.
4. Add result artifact collection independent of provider log retention.
5. Make cleanup idempotent and verify compute plus artifact deletion.
6. Harden redaction, MCP behavior, CI, versioning, installation, and release proof.
7. Add Vultr only by implementing the proven contract.

## User-visible state model

```text
planned
   |
   v
submitting ---- submission failure ----> failed
   |
   v
queued ----> running ----> succeeded
   |             |             |
   |             v             v
   +---------> failed      collecting_results
   |                           |
   v                           v
cancelling ----------------> cleaning
                               |
                     +---------+---------+
                     v                   v
                  cleaned         cleanup_failed
```

Every transition records its time and provider evidence. Repeating status, cancel,
result collection, or cleanup must be safe.

## Provider contract

Each compute adapter must implement:

1. readiness and identity
2. plan
3. submit, returning stable provider job identity
4. status, returning a normalized state
5. logs scoped to one job
6. collect results
7. cancel
8. cleanup
9. verify cleanup
10. classify retryable and terminal failures

Provider-specific values stay inside the adapter and stored provider evidence.
Callers and MCP tools use only the common workload and lifecycle contract.

## Success criteria

- A remote job's durable Elsewhere state matches its actual provider state.
- Fly and Azure pass the same lifecycle conformance suite.
- Short jobs retain stdout, stderr, exit code, and requested result files after
  ephemeral compute disappears.
- `job-cleanup` deletes and verifies compute and source artifacts, and is safe to
  repeat.
- No credential or signed URL appears in plans, attempts, errors, saved jobs, logs,
  MCP results, or test artifacts.
- The Python 3.11, 3.12, and 3.13 matrix is deterministic and green.
- Package, plugin, CLI, MCP server, changelog, tag, and release use one version.
- A fresh installation completes real Fly and Azure jobs after the originating
  machine disconnects.

## Public tracking policy

Create a public `v0.2: Dependable remote execution` milestone. Track lifecycle,
results, cleanup, adapter structure, conformance testing, deterministic CI,
versioning, MCP behavior, and the release gate publicly.

Use private vulnerability reporting for credential exposure, live signed URLs,
personal provider identifiers, or an actionable exploit. A sanitized public follow-up
can document the outcome after remediation.

## Not in scope

- Go or Rust rewrite: deferred until the stable contract reveals a real delivery
  constraint.
- Vultr or other new compute adapters: deferred until Fly and Azure pass conformance.
- Dynamic cost optimization or provider bidding: depends on dependable lifecycle and
  measured provider data.
- A new sandbox runtime: use OpenSandbox, OpenShell, or provider isolation.
- Windows local admission: Linux support and remote lifecycle come first.

## The assignment

Make ten real remote runs on the v0.2 implementation, disconnect the originating
machine after acceptance, and publish a sanitized evidence table showing result
retrieval and verified cleanup for every run.

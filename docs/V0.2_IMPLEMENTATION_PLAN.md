# Elsewhere v0.2 implementation plan

Status: completed in v0.2.0a1
Design: [V0.2_DESIGN.md](V0.2_DESIGN.md)
Milestone: https://github.com/talvinder/elsewhere/milestone/1

## Product intent

An accepted remote job must remain understandable while the originating machine is
asleep or temporarily offline. When that device resumes, the user should receive one
truthful state, one exact outcome, and one cleanup result regardless of which provider
ran the work.

## What already exists

- Atomic local leases and managed local jobs
- Persistent job records guarded by file locks
- Dry provider plans and explicit execution
- Fly and Azure command construction
- A durable trust receipt checked before source upload, submission, and fallback
- Azure Blob source transport with expiring read access
- Source manifests and persisted URL redaction
- CLI, dashboard, skill, and MCP entry points over the same state files

The plan reuses these flows. It does not add a second scheduler, state store, trust
system, or artifact transport.

## Scope challenge

The complete v0.2 roadmap contains several dependent slices. Combining all of them
in one change would mix structural refactoring, provider behavior, artifact design,
security hardening, and release automation. The first implementation slice is the
smallest complete foundation:

1. formal provider adapter contract
2. normalized remote state model
3. provider-scoped status, logs, cancel, cleanup, and cleanup verification
4. durable lifecycle transitions
5. shared conformance tests for Fly and Azure
6. deterministic supported-Python CI

The release completed this foundation and the dependent result, MCP, security, and
acceptance slices. A language rewrite and new providers remain deferred.

## Architecture

```text
CLI / MCP / dashboard
          |
          v
   lifecycle service
    |      |      |
    |      |      +------> persistent job record
    |      +-------------> artifact store
    +--------------------> provider registry
                                |
                     +----------+----------+
                     v                     v
                 Fly adapter          Azure adapter
```

### Provider adapter

Each adapter owns provider vocabulary and implements:

- readiness and configured identity
- plan construction
- submission evidence parsing
- job-scoped status
- job-scoped logs
- normalized failure classification
- cancel
- compute cleanup
- cleanup verification

The lifecycle service owns durable Elsewhere state, transition validation, artifact
cleanup ordering, timestamps, and user-facing summaries.

### Durable state

```text
planned -> submitting -> queued -> running -> succeeded
                   |         |        |          |
                   +---------+--------+--------> failed
                             |                   |
                             v                   v
                         cancelling          cleaning
                             |                   |
                             +-------------------+
                                                 v
                                   cleaned | cleanup_failed
```

Provider status maps into this state machine. Unknown or missing provider resources
do not silently mean success. They preserve the last known state and attach explicit
evidence until completion or deletion can be proved.

## Code organization

Target modules for the first slice:

- `models.py`: state constants, transition rules, normalized provider observations
- `providers/base.py`: adapter protocol and shared result types
- `providers/fly.py`: Fly plans and lifecycle operations
- `providers/azure.py`: Azure plans and lifecycle operations
- `providers/__init__.py`: registry
- `cli.py`: the first slice's refresh, cancel, cleanup, persistence, parsing, and
  presentation; lifecycle orchestration moves to `lifecycle.py` after the adapter
  seam proves stable

Existing local admission and source packaging can remain in `cli.py` initially. This
keeps the structural change attached to remote lifecycle rather than turning v0.2
into a full rewrite.

## Test strategy

Use the standard library test framework so the package retains no runtime dependency.
Add focused standard-library tests while preserving the procedural integration
coverage. Splitting the remaining integration script is tracked separately so the
lifecycle change does not silently drop established behavior.

```text
CODE PATH COVERAGE
==================
Provider contract
├── readiness and identity
├── plan
├── submit evidence
├── status mapping
├── scoped logs
├── cancel
├── cleanup
├── cleanup verification
└── retryable versus terminal failure

Lifecycle service
├── every allowed transition
├── rejected backwards or impossible transition
├── missing provider resource
├── repeated status refresh
├── cancel before and during execution
├── repeated cleanup
├── partial cleanup failure
├── artifact deletion failure
└── persisted evidence redaction

USER FLOW COVERAGE
==================
Plan only ───────────────────────────────> no mutation
Submit ──> queued ──> running ──> success ──> cleanup
Submit ──> failure ────────────────────────> cleanup
Running ──> cancel ──> cancelled ─────────> cleanup
Completed provider resource missing ──────> explicit unknown, never false success
Originating process gone ──> new process refreshes state and continues cleanup
```

Every adapter runs the same conformance cases with realistic provider JSON and CLI
responses. Provider-specific tests cover only translation details.

### Critical regressions

- The Python 3.12 renewal timing race must have a deterministic test.
- Existing dry-run, trust receipt, fallback, source packaging, queue, sampler, and
  local lease behavior must remain covered.
- Saved commands, attempts, errors, logs, and MCP results must reject signed URL
  persistence.

## Failure modes

| Failure | Expected behavior | User-visible result |
|---|---|---|
| Provider submit times out after creating compute | Reconcile by provider job name or identity | Submitted, failed, or unknown with recovery command |
| Fly Machine exits before status refresh | Use retained result/provider evidence; never infer success from absence | Exact result or explicit result unavailable |
| Provider returns malformed JSON | Preserve last state and attach parse failure | Clear retryable status error |
| Cancel races with natural completion | Refresh, accept either terminal outcome, continue cleanup | Truthful terminal state |
| Cleanup runs twice | Treat already absent resources as success | Cleaned with prior/absent evidence |
| Artifact deletion fails after compute deletion | Persist partial cleanup | Cleanup failed with exact remaining resource class |
| Process crashes while writing state | Atomic replacement retains the previous complete record | Recoverable prior state |
| Provider error echoes a signed URL | Redact before persistence and presentation | Sanitized error only |

## Performance

Remote lifecycle commands are network-bound and low-volume. Python is not a material
constraint for v0.2. Avoid background polling in the first slice; refresh explicitly
through status, queue, dashboard, and MCP calls. Bound provider output retained in
job state and keep file-lock critical sections free of provider network calls.

## Implementation order

1. Fix the deterministic baseline test and version drift.
2. Add state and provider contract modules without changing CLI behavior.
3. Migrate Fly and Azure planning behind the registry.
4. Add job-scoped status, logs, cancellation, cleanup, and persisted transitions.
5. Add conformance tests and delete superseded conditional paths.
6. Add result manifests, upload/download lifecycle, and cleanup ordering.
7. Harden redaction and MCP validation.
8. Run fresh-install and live provider acceptance proof.
9. Tag v0.2 alpha only after all gates pass.

## Worktree strategy

Sequential implementation. The first five steps all touch the lifecycle contract and
test fixtures, so parallel worktrees would create more merge risk than useful speed.
Result artifacts and MCP hardening can split into separate lanes only after the
provider contract lands.

## Not in scope

- Go or Rust rewrite
- Vultr adapter
- provider bidding or dynamic price optimization
- new isolation runtime
- UI redesign
- Windows local admission

## Release gate

- All supported Python versions green
- Fly and Azure conformance green
- No unresolved P1 lifecycle or cleanup findings
- Fresh install verified
- Ten real disconnect-and-return runs documented
- Result and cleanup evidence retained without credentials or signed URLs
